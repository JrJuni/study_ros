4. Isaac Sim에서 관절을 직접 움직인다.
5. ROS 2 Bridge로 ROS 2와 Isaac Sim을 연결한다.
6. ROS 2에서 보낸 목표 각도로 관절을 움직인다.

**1자유도(1-DOF)**는 독립적으로 움직일 수 있는 방향이 하나라는 뜻이다.
문에 달린 경첩처럼 한 축을 중심으로만 회전하는 관절이 대표적인 예다.

## 2. [ROS 2와 시뮬레이션 기초] 도구의 역할 구분하기

### 주제

ROS 2, URDF, Omniverse와 Isaac Sim의 역할을 구분한다.

### 학습 목표

- ROS 2가 Ubuntu를 대신하는 운영체제가 아님을 설명할 수 있다.
- URDF를 로봇 구조를 적는 XML 형식의 설계도라고 설명할 수 있다.
- Omniverse와 Isaac Sim의 관계를 구분할 수 있다.
- 노드와 토픽의 기본 역할을 설명할 수 있다.

### 내용 설명

**ROS 2(Robot Operating System 2)**는 로봇 프로그램을 작은 단위로 나누고
서로 통신하게 해 주는 도구 모음이다. 이름에 Operating System이 들어가지만
Windows나 Ubuntu를 대체하지 않는다.

- **노드(Node)**: 카메라 읽기나 모터 제어처럼 한 가지 역할을 맡는 프로그램 단위
- **토픽(Topic)**: 노드들이 계속 흐르는 데이터를 주고받는 이름 있는 통신 통로
- **메시지(Message)**: 토픽을 통해 전달되는 데이터 형식

학교 방송에 비유하면 방송부는 publisher, 방송 채널은 topic, 방송을 듣는
교실은 subscriber다. 실제 ROS 2에서는 노드가 토픽에 메시지를 발행하고 다른
노드가 같은 토픽을 구독한다.

**URDF(Unified Robot Description Format)**는 몸체인 `link`와 몸체를 연결하는
`joint`를 XML로 기록하는 로봇 설계도다.

**Omniverse**는 3D 장면과 도구를 연결하는 NVIDIA의 기반 기술이고,
**Isaac Sim**은 그 기반 위에서 로봇, 센서와 물리 현상을 시뮬레이션하는
애플리케이션이다.

### 예제 또는 실습

실습 상태: 이해 확인

1. 몸체 두 개와 회전축을 글로 표현한다. → URDF
2. 가상 공간에서 중력과 관절 움직임을 계산한다. → Isaac Sim
3. 목표 관절 각도를 다른 프로그램으로 전달한다. → ROS 2
4. 3D 장면의 기반 기술과 USD 데이터를 다룬다. → Omniverse

성공 확인: 네 도구를 모두 “로봇 프로그램”이라고 뭉뚱그리지 않고 각각의
역할을 한 문장씩 말할 수 있으면 된다.

## 3. [설치와 환경 점검] 설치 전 컴퓨터 정보 확인하기

### 주제

설치 전에 운영체제, CPU 구조, NVIDIA GPU, VRAM, RAM과 저장 공간을 확인한다.

### 학습 목표

- 설치보다 환경 점검을 먼저 해야 하는 이유를 설명할 수 있다.
- GPU 이름, VRAM, 드라이버, RAM과 남은 저장 공간을 확인할 수 있다.
- 확인 결과를 바탕으로 설치 방법을 결정할 준비를 할 수 있다.

### 내용 설명

2026년 8월 2일 기준으로 우선 검토할 조합은 Ubuntu 24.04, ROS 2 Jazzy,
Isaac Sim 6.0.1과 Python 3.12다. NVIDIA는 Isaac Sim의 ROS 2 환경으로
Ubuntu 24.04와 ROS 2 Jazzy를 권장한다. 학생 컴퓨터 사양을 확인하기 전에는
이 조합을 최종 확정하지 않는다.

Isaac Sim은 실시간 3D 그래픽과 물리 계산을 수행하므로 높은 GPU 사양이 필요하다.
공식 x86_64 최소 사양에는 RAM 32GB, SSD 여유 공간 50GB, GeForce RTX 4080과
VRAM 16GB가 적혀 있다. **VRAM**은 그래픽 카드가 3D 데이터를 저장하는 전용
메모리이며 컴퓨터 전체 메모리인 RAM과 다르다.

실제 컴퓨터를 점검한 결과는 다음과 같다.

| 항목 | 확인 결과 | 판정 |
| --- | --- | --- |
| 운영체제 | Ubuntu 24.04.4 LTS | ROS 2 Jazzy와 Isaac Sim 지원 환경 |
| CPU 구조 | x86_64 | 지원 환경 |
| CPU | AMD Ryzen 5 7500F, 6코어 12스레드 | 공식 최소 CPU·코어 기준 충족 |
| GPU | NVIDIA GeForce RTX 4070 Ti SUPER | 공식 최소 RTX 4080보다 낮아 주의 필요 |
| VRAM | 16,376 MiB, 약 16GB | 공식 최소 VRAM 기준 충족 |
| 드라이버 | 595.84 | 설치되어 있으며 일반 터미널에서 GPU 인식 성공 |
| RAM | 설치 용량 약 32GB, 표시 용량 31GiB | 공식 최소 기준 충족, 여유는 크지 않음 |
| Swap | 8GB | 메모리 부족 시 보조 공간으로 사용 가능 |
| 저장 공간 | 전체 500GB, 여유 450GB | 설치와 기본 실습에 충분 |
| Python | 3.12.3 | Ubuntu 24.04 및 ROS 2 Jazzy 기본 환경과 일치 |

종합하면 ROS 2 Jazzy 학습 환경은 적합하다. Isaac Sim 6.0.1은 VRAM, RAM과
저장 공간을 충족하지만 GPU 모델이 공식 최소 사양보다 낮다. 따라서 복잡한 센서나
큰 장면부터 시작하지 않고 공식 호환성 검사 후 단순한 1관절 장면으로 시작한다.

### 예제 또는 실습

실습 상태: 완료 — 기본 환경 정보를 수집하고 1차 판정을 마쳤다.

Ubuntu 터미널:

```bash
# Ubuntu 버전과 CPU 구조를 확인한다.
cat /etc/os-release
uname -m

# GPU 이름, VRAM과 드라이버 버전을 확인한다.
nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv,noheader

# RAM과 루트 디스크의 남은 공간을 확인한다.
free -h
df -h /

# 기본 Python 버전을 확인한다.
python3 --version
```

Windows PowerShell:

```powershell
# Windows 버전, CPU 구조와 RAM을 확인한다.
Get-ComputerInfo |
  Select-Object WindowsProductName, WindowsVersion, OsArchitecture, CsTotalPhysicalMemory

# GPU 이름, VRAM과 드라이버 버전을 확인한다.
nvidia-smi --query-gpu=name,memory.total,driver_version --format=csv,noheader

# C 드라이브의 크기와 남은 공간을 확인한다.
Get-Volume -DriveLetter C | Select-Object SizeRemaining, Size

# WSL 상태를 확인한다.
wsl --status
```

성공 확인: 운영체제, CPU 구조, GPU, VRAM, 드라이버, RAM과 저장 공간을 표로
정리할 수 있으면 된다. 명령이 실패하면 오류 문구도 중요한 점검 결과다.

참고: Codex의 제한된 샌드박스 안에서는 `nvidia-smi`가 GPU 장치에 접근하지
못할 수 있다. 일반 Ubuntu 터미널에서 명령이 성공한다면 그 결과를 실제 호스트
환경의 판정 기준으로 사용한다.

## 4. [검증과 문제 해결] Codex Linux 샌드박스 복구하기

### 주제

오류 문구를 근거로 `bwrap`와 AppArmor 문제를 진단하고 안전하게 해결한다.

### 학습 목표

- 증상과 원인을 구분할 수 있다.
- 커널 로그에서 AppArmor의 권한 거부 기록을 찾는 이유를 설명할 수 있다.
- 전역 보안 설정을 끄기 전에 전용 프로파일을 사용하는 이유를 설명할 수 있다.

### 내용 설명

처음에는 Codex가 파일을 편집할 때 다음 오류가 발생했다.

```text
bwrap: loopback: Failed RTM_NEWADDR: Operation not permitted
```

커널 로그에서는 AppArmor가 `bwrap`의 `net_admin`과 `setpcap` capability를
거부한 사실을 확인했다. Landlock 미지원이나 Docker 중첩이 아니라 Ubuntu의
AppArmor user namespace 제한과 `bwrap` 전용 프로파일 부재가 원인이었다.

`apparmor-profiles`와 `apparmor-utils`를 설치하고
`bwrap-userns-restrict` 프로파일을 로드한 뒤 일반 Codex 명령과 파일 편집이
정상 동작했다.

또한 Codex 0.146.0에서는 `codex sandbox linux ...`가 아니라
`codex sandbox -- ...` 문법을 사용한다. 전자는 `linux`를 실행할 프로그램
이름으로 해석해 `Failed to execvp linux` 오류를 냈다.

### 예제 또는 실습

실습 상태: 완료

```bash
# bwrap용 AppArmor 프로파일을 시스템 위치에 복사한다.
sudo install -m 0644 \
  /usr/share/apparmor/extra-profiles/bwrap-userns-restrict \
  /etc/apparmor.d/bwrap-userns-restrict

# 프로파일을 재부팅 없이 커널에 로드한다.
sudo apparmor_parser -r /etc/apparmor.d/bwrap-userns-restrict

# 현재 Codex CLI 문법으로 샌드박스를 검사한다.
codex sandbox -- /usr/bin/true
```

실제 결과: 마지막 명령이 오류와 출력 없이 종료됐다.

성공 확인: 이어서 `echo $?`를 실행했을 때 `0`이 나오면 된다.

## 5. [프로젝트 관리] 날짜별 교재와 백로그 남기기

### 주제

새 Codex 세션에서도 작업을 이어 갈 수 있도록 규칙과 현재 상태를 파일로 남긴다.

### 학습 목표

- 날짜별 학습 문서의 파일 이름을 만들 수 있다.
- 각 주제를 네 단계로 정리할 수 있다.
- `BACKLOG.md`를 이용해 새 세션에서 작업을 재개할 수 있다.

### 내용 설명

대화 컨텍스트는 새 세션에서 항상 보장되지 않는다. 반면 Git 저장소의 파일은
계속 남으므로 결정 사항과 미완료 작업을 `BACKLOG.md`에 기록하면 다른 Codex도
그 파일을 읽고 이어갈 수 있다.

학습 기록은 `docs/lesson_YYMMDD.md` 이름을 사용하고 각 주제를
`주제 → 학습 목표 → 내용 설명 → 예제 또는 실습` 순서로 작성한다.

이 저장소는 배포용 제품이 아니라 개인 학습 노트이므로 기본적으로 `main`에서
직접 작업한다. 학습 내용 하나가 정리될 때마다 작은 커밋을 만들고 바로 푸시한다.
별도 브랜치와 Pull Request는 특별히 검토 과정이 필요할 때만 사용한다.

### 예제 또는 실습

실습 상태: 완료

새 세션에서 다음과 같이 요청한다.

```text
BACKLOG.md를 먼저 읽고, 미완료 작업부터 이어서 진행해줘.
기존 사용자 파일을 보존하고 완료한 항목은 체크해줘.
```

성공 확인: 새 세션이 프로젝트 목표, 결정 사항과 다음 작업을 다시 설명할 수
있으면 된다.

일반적인 학습 기록 반영 순서는 다음과 같다.

```bash
# 최신 원격 학습자료를 먼저 받아온다.
git pull --ff-only origin main

# 이번 학습과 관련된 파일만 추가하고 기록한다.
git add AGENTS.md BACKLOG.md docs/
git commit -m "Update ROS study notes"

# 개인 학습 저장소의 main에 바로 올린다.
git push origin main
```
